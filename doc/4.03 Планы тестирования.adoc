== 1. Управление качеством решения

=== 1.1. Подходы к повышению надёжности

* **Автоматизированное тестирование** – покрытие unit, интеграционных, e2e тестов не менее 80%. Для Java используются JUnit 5, Testcontainers, MockMvc, WireMock.
* **Code review** – обязательный peer review для каждого MR.
* **Feature flags** – возможность включать/отключать функциональность без развертывания.
* **Chaos engineering** – регулярные эксперименты по внесению сбоев (например, отказ узла Kubernetes) для проверки устойчивости.
* **Ретроспективы инцидентов** – анализ каждой проблемы с обязательным документированием и устранением корневых причин.

=== 1.2. Регламентные процессы

* **Еженедельные релизы** – по понедельникам для non‑critical, по средам для critical (с ручным подтверждением).
* **Ежедневные smoke‑тесты** после обновления staging.
* **Ежемесячный анализ метрик** – тренды ошибок, latency, использование ресурсов.
* **Квартальное нагрузочное тестирование** – проверка запаса прочности.

=== 1.3. Автоматизация

* Автоматическая проверка код‑стайла (Checkstyle, Spotless) в CI.
* Автоматическое создание и обновление документации по API (Spring REST Docs / OpenAPI).
* Автоматическое создание релизных заметок на основе изменений в Changelog.

== 2. Испытания

=== 2.1. Автоматизация тестирования

[cols="1,3,3", options="header"]
|===
| Тип тестов | Инструмент (Java‑стэк) | Что проверяется
| Unit-тесты | JUnit 5, Mockito | Логика компонентов, граничные условия, изолированное тестирование сервисов
| Интеграционные | Testcontainers, Spring Boot Test | Взаимодействие сервисов с БД, Kafka, кэшем, внешними API (WireMock)
| API-тесты (контракты) | Spring MockMvc / RestAssured | Валидация REST-эндпоинтов, сериализация/десериализация, HTTP-коды
| E2E (backend) | Testcontainers + Spring Boot Test | Сквозные сценарии: создание объявления → заказ → оплата (без UI)
| E2E (UI) | Cypress / Playwright (отдельно) | Сквозные сценарии с браузером для веб-интерфейса (если будет тестироваться фронт)
| Безопасность | OWASP ZAP, Trivy, SpotBugs | Сканирование уязвимостей API и образов, статический анализ кода
|===


Все тесты запускаются в CI на каждый push. Для успешного мержа требуется прохождение всех стадий.

=== 2.2. Нагрузочное тестирование

**Инструмент:** K6 (JavaScript) или Gatling (Java). Выбран K6 как универсальный, поддерживающий написание сценариев на JavaScript и легко интегрируемый в CI.

**Сценарии:**

1. **Базовый профиль** – имитация реального пользовательского поведения (95% чтения, 5% записи) в течение 30 минут.
2. **Пиковая нагрузка** – внезапное увеличение RPS до 1.5× от расчётной (25 000 → 37 500) на 5 минут.
3. **Длительная стабильность** – 12 часов работы с постоянной нагрузкой 20 000 RPS.
4. **Сбой внешних зависимостей** – отключение платёжного шлюза или службы доставки (эмулируется WireMock в тестовом окружении).

**Критерии успеха:**

* Latency p95 не превышает целевые значения (500 мс для поиска, 1 с для платежей).
* Error rate < 0.1% (кроме тестов сбоев, где проверяется graceful degradation).
* Потребление CPU/RAM не выходит за пределы лимитов.

**Автоматизация:**

* Нагрузочные тесты запускаются по расписанию (ночь) или вручную при релизе.
* Результаты нагрузочных тестов сохраняются в Prometheus (через экспорт метрик) и визуализируются в Grafana. При необходимости для долговременного хранения может использоваться InfluxDB или TimescaleDB..

=== 2.3. Контрактные тесты (Consumer‑Driven Contracts)

Для обеспечения совместимости между микросервисами используются **контрактные тесты** по модели consumer‑driven. Это позволяет проверить, что провайдер API (например, Order Service) соответствует ожиданиям всех своих потребителей (например, Payment Service, Delivery Service).

**Процесс:**
1. **Consumer** (например, Order Service) пишет тест, в котором описывает ожидаемый запрос и ответ от провайдера. Pact генерирует контракт (JSON‑файл).
2. Контракт публикуется в **Pact Broker** (общий репозиторий).
3. **Provider** (например, Payment Service) забирает контракт из Pact Broker и проверяет, что его реальный API соответствует контракту (запускает pact‑verification).
4. Результаты верификации отправляются обратно в Pact Broker, что даёт панель совместимости.

**Периодичность:** при каждом изменении consumer‑а (в CI) и отдельно по расписанию для провайдеров (например, ночью).

**Критерии успеха:** все контракты провайдера зелёные, нет breaking changes. При изменении контракта consumer и provider должны быть обновлены согласованно (помогает Pact Broker с can-i-deploy).
