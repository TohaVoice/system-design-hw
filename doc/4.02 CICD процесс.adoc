== 1. Общий пайплайн

CI/CD реализован с использованием **GitHub Actions**. Пайплайн состоит из стадий, которые выполняются автоматически при пуше в репозиторий, создании pull request или тегировании релиза.

=== 1.1. Стадии CI/CD

[cols="1,2,2", options="header"]
|===
| Стадия | Действия | Условия
| **build** |
* Сборка Docker-образа
* Запуск unit-тестов
* Линтинг кода (SonarQube)
| Всегда (push, pull request)
| **test** |
* Интеграционные тесты с зависимостями (тестовая БД, Kafka)
* Безопасность (Trivy)
| Всегда (для pull request)
| **publish** |
* Публикация образа в GitHub Container Registry (GHCR)
* Обновление Helm-чарта (версия образа)
| Только для `main` и тегов
| **deploy-staging** |
* Применение Helm-чарта к staging-кластеру
* Проверка health endpoints
| Для `main` (после успешного publish)
| **load-test** |
* Запуск нагрузочных тестов (K6) против staging
| Ночной запуск по расписанию или вручную
| **deploy-prod** |
* Blue/Green развертывание в production
* Автоматический откат при ошибке
| По тегу (ручное подтверждение через GitHub Environments)
|===

=== 1.2. Управление версиями

* Ветка `main` – последняя стабильная версия (разворачивается в staging).
* Теги вида `vX.Y.Z` – релизные версии (разворачиваются в production).
* Каждый коммит в ветку `main` собирает образ с тегами:
** `latest`
** `sha-<commit-hash>`
** `branch-main-<short-hash>` (опционально)
* Релизный тег создаёт образ с тегом `vX.Y.Z` и обновляет `latest`.

== 2. Обновления без простоев

=== 2.1. Стратегии развертывания

* **Rolling update (по умолчанию)** – для сервисов без критической нагрузки (например, User Service). Kubernetes постепенно заменяет старые поды новыми. Во время обновления приложение остаётся доступным, но часть трафика может временно направляться на старую версию.
* **Blue/Green deployment** – для критических сервисов (Order Service, Payment Service). Сначала разворачивается «зелёная» версия, затем трафик переключается с «синей». При обнаружении проблем переключение отменяется.
* **Canary deployment** – для A/B тестирования. Часть трафика (например, 5%) направляется на новую версию, затем доля увеличивается постепенно (реализуется через Istio или Flagger).

=== 2.2. Механизмы обеспечения zero‑downtime

* **Readiness probes** – под считается готовым только после успешного прохождения внутренних проверок.
* **Graceful shutdown** – при остановке под завершает текущие запросы перед выходом.
* **Прерывание соединений** – использование подов с несколькими репликами, распределёнными по разным узлам.
* **Базы данных** – обновление с переключением master (Patroni) или миграции схемы без блокировок с использованием:
  ** **pgroll** – управление миграциями с zero‑downtime (многофазные изменения, автоматический откат).
  ** **pg_repack** – онлайн‑реорганизация таблиц и индексов без блокировок записи.
  ** **Liquibase** – для версионных миграций схемы (DDL) в связке с pgroll.


== 3. Обработка сбоев и откат

* Если после развертывания в production падает более 5% запросов (метрика `error_rate`), автоматически инициируется откат.
* Откат выполняется через Helm `rollback` или переключение трафика обратно на «синюю» версию.
* Все действия логируются, инцидент создаётся в Jira (или GitHub Issue).
* GitHub Actions имеет встроенную возможность автоматического отката через `on.failure` или использование ручных проверок в environments.

== 4. Инструменты автоматизации

* **GitHub Actions** – пайплайны сборки, тестирования, публикации.
* **ArgoCD** – синхронизация кластера с Git (GitOps). Отвечает за развертывание в Kubernetes.
* **Helm** – управление релизами.
* **K6** – нагрузочное тестирование.
* **SonarQube** – статический анализ кода (интеграция через GitHub Actions).
* **Trivy** – сканирование уязвимостей образов (запускается в workflow).

== 5. Управление секретами в CI/CD

* **Единое хранилище секретов** – **HashiCorp Vault**
* В GitHub Secrets хранится **только один секрет** – `VAULT_TOKEN` (временный токен для аутентификации GitHub Actions в Vault). Этот токен имеет ограниченные права (только на чтение необходимых секретов для текущего окружения).
* **Процесс получения секретов в пайплайне:**
  1. GitHub Action аутентифицируется в Vault, используя `VAULT_TOKEN`.
  2. Запрашивает динамические секреты:
     * `kubeconfig` для доступа к кластеру Kubernetes (staging/production).
     * Токен для аутентификации в ArgoCD.
     * Учётные данные для доступа к реестру образов (GHCR).
  3. Все секреты передаются в шаги workflow через переменные окружения, не попадая в логи.
* **Ротация секретов** осуществляется через Vault (автоматическая смена паролей БД, токенов сервисов). GitHub `VAULT_TOKEN` также ротируется регулярно (каждые 30 дней) через административный интерфейс.
* **Аудит** – все обращения к Vault из CI/CD логируются и доступны для анализа.

Такой подход централизует управление секретами, исключает дублирование и соответствует общей архитектуре безопасности.

== 6. Взаимодействие с ArgoCD (GitOps)

После публикации образа и обновления Helm-чарта, ArgoCD автоматически синхронизирует кластер (режим auto‑sync). Пайплайн GitHub Actions не выполняет прямое развертывание – он лишь обновляет репозиторий манифестов, а ArgoCD сам применяет изменения.

Это обеспечивает единый источник истины (Git) и позволяет легко откатить изменения через Git revert. Для критических окружений auto‑sync может быть отключён, и требуется ручное подтверждение в ArgoCD UI.

== 7. Мониторинг CI/CD

* Все запуски workflow видны в GitHub Actions с детальными логами.
* Метрики успешности развертываний передаются в Prometheus (через webhook или интеграцию с GitHub).
