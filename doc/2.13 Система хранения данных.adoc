* Размер медиа на одно объявление: 10 фото × 500 KB = 5 MB

== 2. Детализация применения систем хранения данных

=== 2.1. Реляционные базы данных (PostgreSQL)

**Назначение:** Пользователи, заказы, платежи (транзакционные данные, требующие ACID).

**Класс системы:** Реляционная СУБД (ACID‑compliant), объектно‑реляционная.

**Обоснование выбора:**

* Строгая согласованность данных (ACID)
* Сложные транзакции с несколькими таблицами
* Поддержка внешних ключей и ссылочной целостности
* Зрелость, богатый инструментарий, поддержка JSONB

**Конфигурация:**

* **Шардинг:** 2 шарда по **buyer_id** (для `orders`). Запросы продавца (`WHERE seller_id = ?`) не выполняются напрямую в PostgreSQL – они идут в **read‑модель**, построенную в Elasticsearch (денормализованные данные заказов, шардированные по `seller_id`). Это исключает cross‑shard запросы и обеспечивает высокую производительность.
* **Репликация:** **Master + 2 синхронные реплики** на каждый шард.
* **Хранилище:** NVMe SSD (4–8 TB на ноду).
* **Память:** 64 GB RAM (shared_buffers = 16 GB, work_mem = 256 MB).
* **Пул соединений:** pgBouncer.

**Подходы к масштабированию:**

* **Горизонтальное:** Шардинг по buyer_id для основных запросов покупателя; для продавца – отдельная read‑модель в Elasticsearch.
* **Вертикальное:** Read replicas для распределения нагрузки чтения; увеличение ресурсов ноды.
* **Технологии:** Patroni для автоматического failover, etcd/Consul для координации.

**CAP теорема:** **CP (Consistency + Partition Tolerance)** — жертвуем доступностью ради согласованности при разделении сети, что критично для финансовых операций. В случае потери связи с репликами мастер перестает принимать записи, чтобы избежать рассинхронизации.

**Ограничения выбранного решения:**

* Сложность горизонтального масштабирования (шардинг требует изменений в логике приложения и усложняет запросы).
* Размер одной БД не должен превышать 4–8 TB для комфортной работы.
* Запросы продавца выполняются к read‑модели (Elasticsearch), что даёт eventual consistency (задержка до нескольких секунд).
* Требует тюнинга параметров под нагрузку.

**Хранение и наполнение бэкапов, резервных систем:**

* **Инструменты:** pg_basebackup (физические бэкапы), WAL‑G (архивирование WAL в S3).
* **Расписание:**
  - Полный бэкап: ежедневно (в час наименьшей нагрузки).
  - WAL‑архивирование: непрерывно (каждый сегмент 16 МБ).
* **Retention:**
  - Ежедневные полные бэкапы: 30 дней.
  - Еженедельные полные бэкапы: 3 месяца.
  - Ежемесячные полные бэкапы: 1 год.
* **Резервное хранилище:** S3 с cross‑region репликацией.
* **Тестирование восстановления:** ежемесячно (разворот из бэкапа в staging‑среду).

=== 2.3. Wide‑column NoSQL (Cassandra) для чата

**Назначение:** История чатов, временные ряды, сообщения, online‑статус.

**Класс системы:** Распределенная wide‑column NoSQL БД (masterless, линейно масштабируемая).

**Обоснование выбора:**

* Линейная масштабируемость (добавление узлов увеличивает пропускную способность).
* Высокая доступность без единой точки отказа.
* Оптимизирована для запросов по ключу и времени (time‑series).
* Хорошо подходит для append‑only нагрузок (сообщения только добавляются).
* Встроенный TTL для автоматического удаления старых сообщений.

**Конфигурация:**

* Кластер: **5 нод** (репликация factor = 3).
* Конфигурация ноды: 32 GB RAM (heap = 8 GB), 2 TB SSD.
* Стратегия партицирования: по conversation_id + месяц (time‑window compaction).
* Тонкая настройка: TTL для сообщений (12 месяцев).

**Масштабирование:**

* **Горизонтальное:** добавление нод без даунтайма, автоматическая ребалансировка (vnodes).
* Использование виртуальных нод для равномерного распределения нагрузки.

**Высокая доступность и отказоустойчивость:**

* Репликация factor = 3 (данные хранятся на трёх нодах, переживают потерю 2 нод).
* Gossip protocol для обнаружения отказов и распространения информации о состоянии.
* Настраиваемый consistency level (QUORUM, LOCAL_QUORUM, ONE) для баланса между согласованностью и доступностью.

**CAP теорема:** **AP (Availability + Partition Tolerance)** — жертвуем строгой согласованностью (eventual consistency) ради доступности. В случае сетевого разделения Cassandra продолжает принимать записи, конфликты разрешаются по принципу Last Write Wins. Для чата это приемлемо.

**Ограничения выбранного решения:**

* Нет JOIN и сложных запросов (все данные должны быть денормализованы).
* Ограниченные возможности вторичных индексов (рекомендуется создавать отдельные таблицы для альтернативных ключей доступа).
* Операции обновления/удаления неэффективны (tombstones).

**Хранение и наполнение бэкапов, резервных систем:**

* **Инструменты:** nodetool snapshot (снапшоты), копирование в S3.
* **Расписание:** ежедневные снапшоты.
* **Retention:** 7 дней (быстрое восстановление), ежемесячные снапшоты — 3 месяца.
* **Восстановление:** развертывание нового кластера и загрузка снапшотов.
* Тестирование восстановления — ежеквартально.

=== 2.4. Брокер сообщений (Kafka)

**Назначение:** Асинхронная коммуникация между сервисами, обмен событиями, потоковая обработка.

**Класс системы:** Распределенный журнал (log) с поддержкой pub/sub.

**Обоснование выбора:**

* Высокая пропускная способность и низкая задержка.
* Устойчивость к потере данных (репликация, retention).
* Возможность воспроизведения событий (replay).
* Разделение сервисов (слабая связанность).

**Конфигурация:**

* Кластер: **5 брокеров** (репликация factor = 3 для критичных топиков).
* Память: 16 GB RAM на брокер, диски: NVMe SSD.
* Retention: 7 дней для основных топиков, 30 дней для аудита.
* Партиции: в зависимости от пропускной способности топика (10–20 партиций на топик).
* Сжатие: snappy для экономии места.

**Масштабирование:**

* **Горизонтальное:** добавление брокеров, увеличение количества партиций.
* Использование Kafka Streams для потоковой обработки.

**Высокая доступность и отказоустойчивость:**

* Репликация партиций (минимум 3 реплики).
* Автоматическое восстановление лидера при сбое.
* Multi‑AZ развертывание для критических топиков.

**CAP теорема:** **AP (Availability + Partition Tolerance)** — в случае сетевого разделения Kafka может продолжать обслуживать записи и чтения в каждой из разделенных частей, но гарантии согласованности зависят от настроек `min.insync.replicas` и `acks=all`. При `acks=all` и достаточном количестве синхронизированных реплик можно приблизиться к CP, но ценой доступности.

**Ограничения выбранного решения:**

* Хранение данных в течение заданного времени (retention), данные не удаляются мгновенно.
* Сложность управления схемами событий (требуется Schema Registry).
* Нет встроенной поддержки транзакций между разными топиками (до версии 2.8 — только внутри одного топика).

**Хранение и наполнение бэкапов, резервных систем:**

* Бэкапирование данных Kafka — сложная задача; обычно применяется mirroring (межкластерная репликация).
* **Стратегия:** MirrorMaker 2 для репликации критичных топиков в DR‑кластер.
* Retention обеспечивает автоматическое удаление старых данных.
* Для долговременного хранения событий — экспорт в S3 через Kafka Connect (S3 Sink Connector).

=== 2.5. Кэширующая система (Redis)

**Назначение:** Сессии пользователей, кэш объявлений (горячие данные), rate limiting, Pub/Sub для чата, счетчики, блокировки.

**Класс системы:** In‑memory key‑value store (структуры данных).

**Обоснование выбора:**

* Микросекундные задержки (субмиллисекундные).
* Поддержка сложных структур данных (hash, list, set, sorted set, HyperLogLog, Bitmaps).
* Pub/Sub для real‑time коммуникаций (чат).
* Поддержка TTL для автоматического истечения срока действия.
* Атомарные операции (INCR, DECR) для rate limiting и счетчиков.

**Конфигурация:**

* Кластер: **3 master + 3 replica** (sentinel для HA) для кэша сессий и данных; отдельно кластер для Pub/Sub (можно использовать тот же, но с разделением).
* Память: 64 GB RAM на мастер‑ноду (политика вытеснения: `allkeys‑lfu` для кэша, `noeviction` для сессий).
* Персистентность: отключена для кэша (чистый кэш), включена AOF + RDB для сессий (каждую секунду).

**Масштабирование:**

* **Горизонтальное:** Redis Cluster (автоматическое шардирование на 16384 слотов).
* Read replicas для распределения нагрузки чтения (кэш).

**Высокая доступность и отказоустойчивость:**

* Redis Sentinel (автоматический failover, мониторинг, уведомления).
* Redis Cluster (репликация шардов, автофейловер на уровне шарда).

**CAP теорема:** **AP (Availability + Partition Tolerance)** – в кластерном режиме при разделении сети кластер может разделиться, и часть узлов продолжит обслуживать запросы, но есть риск потери записей, отправленных в недоступную часть (асинхронная репликация). В режиме Sentinel (master‑slave) система ближе к CP, но при разделении мастер может оказаться в меньшинстве и стать недоступным.

**Ограничения выбранного решения:**

* Данные должны помещаться в RAM (ограничение по объему, дороговизна).
* Персистентность не гарантируется при сбоях без AOF/RDB (может быть потеря последних данных).
* Нет сложных запросов, только по ключу.
* Резкое увеличение памяти при большом количестве ключей с TTL (необходим мониторинг).

**Хранение и наполнение бэкапов, резервных систем:**

* **Инструменты:** `SAVE` / `BGSAVE` (RDB‑файлы), `redis‑cli --rdb`, копирование AOF.
* **Расписание:** ежечасные RDB‑снимки (для сессий), ежедневные – в S3.
* **Retention:** 3 дня (быстрое восстановление), 7 дней для сессий.
* **Восстановление:** загрузка RDB при старте, репликация от мастера.
* Тестирование восстановления — ежемесячно.

=== 2.6. Объектное хранилище (S3)

**Назначение:** Медиафайлы (изображения, видео, документы), резервные копии, логи, статические файлы, архивное хранение.

**Класс системы:** Объектное хранилище (blob storage), совместимое с AWS S3 API.

**Обоснование выбора:**

* Безграничная масштабируемость (емкость > PB).
* Экономичное хранение больших объемов данных (разные классы: Standard, IA, Glacier).
* Встроенная репликация и жизненные циклы (lifecycle policies).
* Доступ через HTTP/REST API (простые интеграции).
* Высокая надежность (durability 11 девяток).

**Жизненные циклы:**

* `media‑prod/` → 0‑30 дней STANDARD, 30‑90 дней STANDARD_IA, 90‑365 дней GLACIER, >365 дней DEEP_ARCHIVE или удаление.
* `backups/` → версионирование + кросс‑регион репликация.
* `logs/` → переход в STANDARD_IA после 7 дней, удаление через 90 дней.

**CAP теорема:** **AP (доступность и устойчивость к разделению)** — согласованность в конечном счете (eventual consistency) после записи. Чтение после записи может вернуть старую версию, но для медиа это приемлемо.

**Ограничения выбранного решения:**

* Нет транзакций и сложных запросов (только GET/PUT/DELETE по ключу).
* Задержки выше, чем у дискового хранилища (миллисекунды для STANDARD, секунды/минуты для Glacier).
* Ограничение на размер одного объекта (5 TB для S3, обычно 5 ГБ для одного PUT, большие объекты через multipart upload).

**Хранение и наполнение бэкапов, резервных систем:**

* Бакеты уже являются хранилищем бэкапов (версионирование включено).
* Версионирование: случайно удаленные/измененные объекты можно восстановить.
* Тестирование восстановления: регулярное скачивание и проверка целостности бэкапов.

== 4. Итоговые рекомендации

1. **PostgreSQL** — основная база для транзакционных данных с шардированием по ключу доступа. Использовать Patroni для failover, WAL‑G для архивации в S3.
2. **Elasticsearch** — 10 нод (32 GB RAM, 2 TB SSD) для поиска. Применить горячие/теплые/холодные узлы, snapshot‑ы в S3.
3. **Cassandra** — 5 нод для истории чатов с TTL 12 месяцев. Репликация factor 3, партицирование по conversation_id + месяц.
4. **Kafka** — 5 брокеров, retention 7 дней для основных топиков, 30 дней для аудита. MirrorMaker 2 для DR.
5. **Redis** — кластер из 3 мастеров + 3 реплики. Политика вытеснения `allkeys‑lfu` для кэша, `noeviction` для сессий.
6. **S3** — медиа с жизненными циклами (STANDARD → IA → Glacier). Бэкапы баз с версионированием.
7. **Холодное хранилище** — S3 Glacier / Glacier Deep Archive для логов аудита (7 лет) и архивных объявлений.
8. **Регулярное тестирование восстановления** — ежемесячно для критичных систем, ежеквартально для остальных.
