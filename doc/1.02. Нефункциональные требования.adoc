= Нефункциональные требования
:icons: font
:toc:

== Базовые параметры системы

**Целевые метрики нагрузки:**

- Пиковая нагрузка: 25,150 RPS
- Активные пользователи: 5M MAU
- Активные объявления: 25M
- Суточная нагрузка: 330.75M запросов
- Объем данных: ~137 TB

**Распределение нагрузки:**

- Advertisement Service (поиск): 20,000 RPS (79.5%)
- Advertisement Service (создание): 2,500 RPS (9.9%)
- User Service: 1,500 RPS (6.0%)
- Chat Service: 750 RPS (3.0%)
- Order Service: 250 RPS (1.0%)
- Payment Service: 150 RPS (0.6%)

== Требования к производительности

=== Advertisement Service
* Поиск объявлений: ≤ 300 мс (p95), ≤ 800 мс (p99)
* Фильтрация по категориям/локации: ≤ 500 мс (p95)
* Создание объявления: ≤ 2 сек (p95) с учетом обработки медиа
* Обновление объявления: ≤ 1 сек (p95)

=== User Service
* Аутентификация (JWT): ≤ 200 мс (p99)
* Загрузка профиля: ≤ 300 мс (p95)
* Регистрация пользователя: ≤ 1 сек (p95)

=== Chat Service
* Доставка сообщения: ≤ 100 мс (p95)
* Подключение WebSocket: ≤ 1 сек (p99)
* Загрузка истории чата: ≤ 500 мс (p95)

=== Order Service
* Создание заказа: ≤ 800 мс (p95)
* Подтверждение заказа: ≤ 500 мс (p95)
* Получение истории заказов (покупатель): ≤ 400 мс (p95)
* Получение списка заказов продавцом: ≤ 500 мс (p95) с eventual consistency (задержка обновления read-модели до 5 секунд)

=== Payment Service
* Инициализация платежа: ≤ 1 сек (p95)
* Проверка статуса платежа: ≤ 300 мс (p95)
* Обработка вебхуков: ≤ 200 мс (p99)

=== Межсервисная коммуникация
* gRPC запросы между сервисами: ≤ 100 мс (p99) в пределах AZ
* HTTP запросы: ≤ 150 мс (p95)
* Задержка Kafka сообщений: ≤ 50 мс (p95)

== Требования к надежности

=== Уровни доступности (SLA)

**Критические сервисы (входят в end‑to‑end сценарий покупки):**
* API Gateway: 99.99%
* User Service: 99.9%
* Advertisement Service: 99.9%
* Order Service: 99.9%
* Payment Service: 99.99%

**Некритические сервисы (не блокируют основную функцию):**
* Chat Service: 99.0% (допустимы кратковременные перерывы)
* Notification Service: 99.0%
* Admin Service: 99.0%

**Общая доступность системы для end‑to‑end операции (поиск → заказ → оплата):**
Произведение индивидуальных SLA критических сервисов даёт ≈ 99.7%. Данный уровень признаётся достаточным на текущем этапе развития сервиса.

=== Восстановление после сбоев

**Целевые RTO/RPO:**
* Критичные сервисы (Payment, Order): RTO ≤ 15 мин, RPO ≤ 5 мин
* Основные сервисы (Advertisement, User): RTO ≤ 30 мин, RPO ≤ 15 мин
* Вспомогательные сервисы (Chat, Notification): RTO ≤ 2 ч, RPO ≤ 1 ч

**Дополнительные требования:**
* Восстановление сервиса (перезапуск): ≤ 2 мин
* Восстановление из бэкапа (критичные данные): ≤ 15 мин
* Восстановление из бэкапа (полное): ≤ 2 часа
* Активация DR региона: ≤ 30 мин

=== Гарантии сохранения данных
* RPO: ≤ 5 минут для транзакционных данных
* RTO: ≤ 30 минут для критичных сервисов
* Гарантия отсутствия потери данных при graceful shutdown
* Транзакционная целостность для финансовых операций

== Требования к согласованности данных

* **Сильная согласованность (ACID)** – для платежей, заказов, резервирования товаров, операций с балансом.
* **Консистентность в конечном счёте (eventual)** – для поиска объявлений, рейтингов, отзывов, уведомлений.
* **Причинная согласованность (causal)** – для сообщений чата (порядок сообщений должен сохраняться).
* Для запросов продавца к списку заказов допускается задержка обновления read‑модели до 5 секунд (eventual consistency), при этом операции подтверждения/отмены заказа используют синхронное обращение к primary storage.

== Требования к масштабируемости

* Stateless сервисы (User, Advertisement, Order, Payment, Chat) должны горизонтально масштабироваться добавлением реплик.
* Автоскейлинг по CPU/RPS: добавление реплик при загрузке >70% в течение 5 минут, удаление при <30% в течение 15 минут.
* Базы данных: шардирование PostgreSQL (orders по buyer_id) с read‑моделью для продавца в Elasticsearch.
* Elasticsearch кластер: добавление data нод при превышении 80% CPU или 80% диска.
* Redis Cluster: горизонтальное масштабирование добавлением мастер-нод (автоматическое перебалансирование слотов).
* Kafka: увеличение количества партиций для горячих топиков, добавление брокеров при росте нагрузки.

== Требования к нагрузочной устойчивости

* Система должна выдерживать пиковую нагрузку 25,150 RPS в течение 30 минут без превышения latency p95 более чем на 20% от целевых значений.
* При резком скачке нагрузки до 1.5× от расчётной (37,725 RPS) допускается временное увеличение latency, но не более чем на 100% в течение 5 минут.
* При выходе из строя одной из зон доступности (AZ) система должна сохранять не менее 70% пропускной способности.

== Метрики SLA/SLO/SLI

|===
| Метрика | SLA | SLO | SLI (Измерение)
| Общая доступность (end‑to‑end) | 99.7% | 99.8% | (uptime) / (total_time) по критическому пути
| Доступность API Gateway | 99.99% | 99.995% | Доля успешных HTTP-запросов (коды 2xx, 3xx)
| Доступность Payment Service | 99.9% | 99.95% | Доля успешных платежей
| Время ответа поиска объявлений | ≤ 800 мс | ≤ 500 мс | p95 latency (Prometheus)
| Время ответа создания заказа | ≤ 1.5 с | ≤ 800 мс | p95 latency
| Успешность операции (создание объявления, заказа, платежа) | 99% | 99.5% | % успешных операций
|===

== Требования к безопасности

* Защита от DDoS на уровне CDN и API Gateway.
* Шифрование PII-данных в покое (AES-256) и при передаче (TLS 1.2+).
* Аутентификация пользователей через OAuth2/JWT, межсервисная аутентификация через сервисные JWT + сетевые политики.
* Аудит всех критичных операций (изменение ролей, модерация, платежи).
* Соответствие PCI DSS для Payment Service.
* Регулярное сканирование уязвимостей (образов, зависимостей).

== Требования к API

* Версионирование REST API через URL path (`/v1/`, `/v2/`). Каждая версия поддерживается не менее 12 месяцев после объявления deprecated.
* Обратная совместимость: добавление новых полей в ответы не должно ломать старых клиентов.
* Для gRPC используется строгая проверка совместимости схем (Protobuf) через Schema Registry.

== Требования к документации

* OpenAPI (Swagger) спецификация для всех публичных REST API должна обновляться при каждом изменении.
* Архитектурные решения и runbooks хранятся в репозитории и проходят ревью.
* Схемы данных (ER-диаграммы) поддерживаются в актуальном состоянии.
