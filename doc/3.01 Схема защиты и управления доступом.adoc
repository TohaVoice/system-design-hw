== 1. Аутентификация и авторизация

=== 1.1. Выбор механизмов

Для обеспечения безопасного доступа к компонентам системы используются следующие механизмы:

* **OAuth 2.0 + OpenID Connect (OIDC)** – для аутентификации пользователей через внешних провайдеров (Google, VK) и внутреннего корпоративного провайдера **Keycloak**.
* **JWT (JSON Web Tokens)** – для передачи утверждений о пользователе и правах доступа между сервисами.
* **Сетевые политики + сервисные JWT** – для аутентификации и авторизации межсервисных вызовов (без mTLS).

**Роль Keycloak:** Keycloak выступает в качестве централизованного Identity Provider (IdP) для администраторов, модераторов и сервисных аккаунтов, а также может использоваться как внешний OIDC-провайдер наравне с Google и VK. Он отвечает за проверку учётных данных (логин/пароль, 2FA) и выдачу внешнего токена (например, JWT от Keycloak). Однако микросервисы не принимают токены Keycloak напрямую.

**Роль User Service:** User Service является адаптером между внешними провайдерами и внутренней системой. После успешной аутентификации у любого внешнего провайдера (Keycloak, Google, VK) User Service:

* Верифицирует полученный внешний токен (проверяет подпись, срок действия, аудиторию).
* Находит или создаёт внутреннюю учётную запись пользователя (связывая внешний `sub` с внутренним `user_id`).
* Назначает внутренние роли (BUYER, SELLER и т.д.) на основе данных из профиля или внешнего токена.
* **Генерирует и выдаёт внутренний JWT** (access token) и refresh token, которые уже используются всеми микросервисами.

=== 1.2. Выдача и проверка токенов

**Схема выдачи токенов:**

1. Пользователь передаёт учётные данные (логин/пароль или OAuth-код) в **User Service** через API Gateway.
2. User Service проверяет учётные данные, генерирует **Access Token** (JWT, время жизни 15 минут) и **Refresh Token** (случайная строка, время жизни 7 дней).
3. Access Token содержит:
   * `sub` – идентификатор пользователя (UUID)
   * `roles` – список ролей (например, `["buyer", "seller"]`)
   * `exp` – время истечения
   * `iat` – время выдачи
   * `jti` – уникальный идентификатор токена (для инвалидации)
4. Refresh Token хранится в Redis (ключ – `refresh:<user_id>`, значение – токен, TTL 7 дней).
5. API Gateway получает оба токена и возвращает их клиенту.

**Проверка токенов:**

* Клиент передаёт Access Token в заголовке `Authorization: Bearer <token>` при каждом запросе.
* API Gateway проверяет подпись токена (используя публичный ключ User Service), срок действия и наличие в «чёрном списке» (Redis).
* Если токен валиден, Gateway извлекает `user_id` и роли и пробрасывает их в заголовки запроса к внутренним сервисам (`X-User-Id`, `X-User-Roles`).
* Внутренние сервисы проверяют наличие этих заголовков и могут дополнительно выполнить авторизацию (например, проверить, что seller_id совпадает с пользователем при редактировании объявления).

=== 1.3. Обновление токенов

Процесс обновления (refresh):

1. Клиент отправляет запрос на эндпоинт `/auth/refresh` с Refresh Token.
2. API Gateway перенаправляет запрос в User Service.
3. User Service проверяет существование токена в Redis и срок его действия.
4. При успехе генерируется новая пара токенов (Access + Refresh), старый Refresh Token удаляется, новый сохраняется в Redis.
5. Ответ с новыми токенами возвращается клиенту.

Если Refresh Token утерян или истёк, пользователь должен пройти аутентификацию заново.

=== 1.4. Межсервисная аутентификация

Для внутренних вызовов между микросервисами используется комбинация **сетевых политик** и **сервисных JWT**:

* **Сетевые политики (Network Policies)** в Kubernetes разрешают только трафик между сервисами, которым необходимо взаимодействовать. Например, Order Service может отправлять запросы только к Payment Service и Delivery Service.
* **Сервисные JWT** – каждый сервис при старте получает от User Service токен, подписанный общим секретом. Токен передаётся в заголовке `X-Service-Token` при каждом вызове. Принимающий сервис проверяет подпись и имя сервиса (claim `service_name`). Если токен недействителен или сервису запрещён доступ к данному эндпоинту, запрос отклоняется.

Все внутренние соединения защищены TLS (используются самоподписные сертификаты или автоматические из Istio). Обязательная взаимная аутентификация сертификатов не требуется, что значительно упрощает эксплуатацию.

== 2. Безопасность передачи данных

=== 2.1. TLS/SSL

* Все внешние соединения (клиент → API Gateway) и внутренние соединения между сервисами защищены TLS версии 1.2 или выше.
* Используются только современные шифры, поддерживающие **Perfect Forward Secrecy (PFS)** (например, `ECDHE-RSA-AES256-GCM-SHA384`).
* Включён **HTTP Strict Transport Security (HSTS)** с `max-age=31536000` и `includeSubDomains` для всех публичных эндпоинтов.
* Сертификаты выпускаются Let's Encrypt (для внешних) или внутренним CA (для внутренних) и автоматически обновляются.

=== 2.2. Шифрование чувствительных данных внутри защищённого канала

Даже при использовании TLS некоторые данные шифруются дополнительно на уровне приложения:

* **Пароли пользователей** – хранятся в БД только в виде bcrypt-хеша (соль индивидуальна).
* **Платежные данные** – перед отправкой в платёжные шлюзы (Stripe, Тинькофф) подписываются с помощью HMAC-SHA256, используя секретный ключ, хранящийся в HashiCorp Vault.
* **Персональные данные (PII)** – шифруются на уровне БД (AES-256-GCM) с ключами, управляемыми через Vault.
* **Секреты в конфигурации** – хранятся только в зашифрованном виде (Vault или Kubernetes Secrets).

== 3. Управление доступами (RBAC)

=== 3.1. Ролевая модель

Система использует ролевую модель (RBAC) с предопределёнными ролями:

* **Покупатель (`BUYER`)** – базовая роль для всех зарегистрированных пользователей, которые приобретают товары. Позволяет просматривать объявления, создавать заказы, совершать оплату, участвовать в чатах, оставлять отзывы.

* **Продавец (`SELLER`)** – расширяет права покупателя возможностью создавать и управлять своими объявлениями, подтверждать или отклонять заказы, просматривать собственную аналитику продаж. Роль назначается после верификации (например, подтверждения номера телефона).

* **Модератор (`MODERATOR`)** – роль для сотрудников, проверяющих контент. Позволяет просматривать очередь объявлений, одобрять или отклонять их, блокировать пользователей-нарушителей, обрабатывать жалобы. Не имеет доступа к финансовой информации и заказам других пользователей.

* **Администратор (`ADMIN`)** – полный доступ ко всем функциям системы, включая управление пользователями (создание, блокировка), настройку системных параметров (тарифы, категории), просмотр всех логов и аудита, управление ролями.

* **Сервисная учётная запись (`SERVICE_ACCOUNT`)** – роль, назначаемая машинным сервисам для межсервисного взаимодействия. Права сервиса определяются отдельно в конфигурации политик доступа (например, `payment-service` может вызывать `/api/v1/orders/*`, но не `/api/v1/users/*`). Токен для такой учётной записи имеет короткое время жизни (до 24 часов) и привязан к конкретному сервису.

=== 3.2. Принципы проверки прав

* **На уровне API Gateway** – проверяется, что роль пользователя включена в список разрешённых для конкретного эндпоинта (конфигурация в OpenAPI или отдельном манифесте).
* **На уровне бизнес-логики сервиса** – дополнительно проверяется, что идентификатор владельца ресурса (например, `seller_id` объявления) совпадает с `user_id` из токена, если только пользователь не имеет роль `ADMIN` (такая проверка выполняется на уровне кода сервиса).
* **Сервисные вызовы** – принимающий сервис проверяет подпись сервисного JWT и сверяет имя сервиса с политикой доступа, хранящейся в Redis (обновляется раз в минуту).

=== 3.3. Управление ролями

* Добавление/изменение ролей выполняется через Admin Service. При изменении роли пользователя создаётся запись в таблице `admin_actions`, а кэш ролей в Redis обновляется.
* Периодически (каждые 5 минут) сервисы перечитывают актуальные политики доступа (для межсервисных вызовов) и список активных ролей.
* Изменение роли не требует перезапуска сервисов; новое правило вступает в силу в течение нескольких минут.

== 4. Хранение и управление секретами

=== 4.1. Выбор инструмента

**HashiCorp Vault** используется для централизованного хранения и управления секретами.

**Схема работы:**

* Каждый микросервис аутентифицируется в Vault с помощью Kubernetes Service Account (через JWT) или AppRole.
* Vault выдает динамические секреты для доступа к базам данных (PostgreSQL, Redis) и внешним API (Stripe, СДЭК, SendGrid).
* Ключи шифрования данных (AES-256) хранятся в Vault и передаются сервисам только при запуске.

=== 4.2. Ротация секретов

* **Пароли БД:** Vault генерирует временные учётные записи для каждого сервиса с ограниченным сроком жизни (до 24 часов). При перезапуске сервиса он получает новый пароль.
* **API-ключи:** для внешних сервисов используется механизм `cubbyhole` с ротацией раз в 30 дней; Vault уведомляет администратора о необходимости обновления.
* **JWT signing keys:** пары ключей (RS256) обновляются каждые 90 дней; старый ключ остаётся валидным ещё 15 дней для верификации токенов, выпущенных до ротации.
* Все изменения секретов логируются и отправляются в систему аудита.

=== 4.3. Шифрование конфигурационных данных

* Конфигурационные файлы (YAML/JSON) не содержат секретов. Вместо них используются переменные окружения, которые ссылаются на секреты Vault.
* Kubernetes Secrets применяются только для начальной загрузки Vault agent (токен и адрес Vault).
