== 1. Логирование событий безопасности

=== 1.1. Категории событий

Все сервисы обязаны логировать следующие типы событий:

[cols="2,5", options="header"]
|===
| Категория | События
| **Аутентификация** |
* Успешный/неудачный вход
* Обновление токена
* Смена пароля
* Регистрация нового пользователя
* Удаление сессии
| **Авторизация** |
* Доступ к ресурсу без достаточных прав (403)
* Попытка выполнения запрещённой операции
| **Управление доступом** |
* Изменение роли пользователя
* Блокировка/разблокировка пользователя
* Создание/удаление сервисного аккаунта
| **Критичные операции** |
* Создание/отмена заказа
* Проведение платежа
* Изменение статуса модерации
* Создание/удаление объявления
| **Доступ к чувствительным данным** |
* Просмотр/экспорт логов аудита
* Доступ к персональным данным (PII) без авторизации
* Чтение секретов из Vault
| **Системные события** |
* Изменение конфигурации безопасности
* Старт/остановка сервиса
* Ошибки подключения к Vault
|===

=== 1.2. Структура логов

Каждая запись лога содержит поля, приведённые в примере ниже. Поля `trace_id` и `request_id` позволяют связать логи разных сервисов в рамках одного запроса (используется Jaeger).

[source,json]
----
{
  "@timestamp": "2025-03-24T10:15:30.123Z",
  "service": "user-service",
  "event_type": "authentication.failed",
  "user_id": "user-123",
  "session_id": "session-456",
  "source_ip": "192.168.1.1",
  "request_id": "req-789",
  "trace_id": "trace-abc",
  "severity": "warning",
  "message": "Invalid password attempt for user@example.com",
  "details": {
    "attempt_count": 3,
    "lockout_remaining": 120
  }
}
----

=== 1.3. Хранение и защита логов

* Логи отправляются в централизованную систему **ELK (Elasticsearch, Logstash, Kibana)**.
* Доступ к логам строго ограничен: только администраторы и служба безопасности могут читать логи аудита.
* Логи аудита (категории выше) сохраняются в отдельном индексе Elasticsearch с retention **7 лет**.
* Для долговременного хранения ежедневно создаётся снапшот в S3 Glacier.

== 2. Мониторинг аномального поведения

=== 2.1. Метрики безопасности

Следующие метрики собираются в Prometheus и отслеживаются в Grafana:

[cols="2,3,3", options="header"]
|===
| Метрика | Описание | Порог срабатывания
| `auth_failures_total` | Количество неудачных аутентификаций за минуту | > 100 для одного IP
| `auth_success_total` | Количество успешных аутентификаций | не нормировано
| `refresh_token_usage` | Частота обновления токенов | резкие скачки (>10x среднего)
| `rbac_denials_total` | Количество запрещённых запросов | > 10 в минуту
| `sensitive_data_access` | Доступ к PII без явной причины (например, массовый экспорт) | > 1000 записей за час
| `vault_connection_errors` | Ошибки подключения к Vault | > 0 за 5 минут
| `tls_cert_expiry_days` | Дни до истечения сертификатов | < 30 (предупреждение), < 7 (критический)
|===


== 3. Инструменты и технологии

[cols="2,2,3", options="header"]
|===
| Компонент | Технология | Назначение
| Управление секретами | HashiCorp Vault | Хранение и ротация секретов, динамические учётные записи БД
| Аутентификация | OAuth2 (Keycloak) / внутренний User Service | Выдача токенов, провайдеры
| API Gateway | Kong | Проверка JWT, маршрутизация
| Сетевые политики | Kubernetes Network Policies | Изоляция трафика между сервисами
| Централизованные логи | ELK Stack | Сбор, хранение, анализ логов
| Мониторинг | Prometheus + Grafana | Метрики безопасности
| Алертинг | Alertmanager + PagerDuty/Slack | Оповещения
|===
